# The Windows child-console policy is owned by a constructor, and guarded by a source census rather than a runtime test

Every child we spawn on Windows needed `CREATE_NO_WINDOW`: the shipped build is a GUI-subsystem process (the `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]` attribute at the top of `src-tauri/src/main.rs`), so it has no console for a console-subsystem child (`cmd.exe`, `fd`, `rg`, an `npx.cmd` shim) to inherit, and Windows allocates a new console — and a new console *window* — for each one (`docs/research/windows-child-console-window.md`; issue #35, shipped as PR #36 / `f8450d42`). We decided to make `agent::childproc` the **only** place in the crate that builds a `Command` (`command()` / `command_std()`, with the flag set inside and `hide_console` kept private), and to guard it with a test that greps our own source for `Command::new(` outside that module — rather than a test that runs something and observes whether a window appeared.

The reason a runtime test is impossible here, and not merely inconvenient: `cargo test` runs as a console-subsystem process, so a child inherits the *test harness's* console whether or not the flag is set — the behaviour cannot be observed from inside it. And neither `std` nor `tokio` has a `get_creation_flags` (rust-lang/rust#96794 exists for exactly that gap), so the flag cannot even be read back off the `Command` we configured; `as_std()` does not help, because `std` has no getter either. That leaves "what the source says" as the only honest introspection, in the same spirit as `hostenv::configured_env`, which is documented as "the only honest introspection available" for the same class of reason.

## Considered Options

- **A post-hoc `hide_console(&mut cmd)` call at each site, with a test that checks each site reaches it (rejected).** It reads better — the policy is visibly applied where the command is built — but the test has to reason about control flow: prove every construction reaches the helper before its `spawn`/`output`, across the `#[cfg(unix)]`/`#[cfg(not(unix))]` pair in the `exec` tool's spawn arm (the `exec.rs` line anchor this sentence used to carry is a dead pointer — that file left this checkout for the `fulcrum-core` crate) where one tool builds two commands. A flow-parsing census is brittle, and brittle tests get deleted rather than fixed. The constructor inverts it into one dumb invariant: there is no `Command` to forget the flag on.
- **Windows CI running a release build and asserting no window appeared (rejected).** It also would not have caught the original: nothing in a headless runner can assert "no window appeared", and the shipped-vs-dev difference that hid the bug in the first place is the parent's subsystem, not the child's. It doubles Windows CI minutes to buy an assertion that cannot be written.
- **No census test — rely on review (rejected).** The bug was possible for three releases precisely because "add a spawn" has no visible obligation attached to it. A one-line grep-level test is cheaper than the review attention it replaces.
- **`DETACHED_PROCESS` instead of `CREATE_NO_WINDOW` (rejected).** Documented to make `CREATE_NO_WINDOW` *ignored* when combined with it, and it leaves the child free to `AllocConsole` later anyway. `CREATE_NO_WINDOW` is the flag whose documented meaning is the intent: "a console application that is being run without a console window".

## Consequences

- **The census test is a lint, and says so.** It proves no site bypasses the module; it does NOT prove the flag suppresses a window — that half stays verified by one manual run of the packaged `target\release\Archimedes.exe` on Windows, recorded in the spec. Anyone reading the test must not be allowed to conclude more than it shows. **Amended 2026-11-06 — the window-suppression half is no longer wholly unverified, and this bullet is narrowed rather than withdrawn.** Issue #156's reporter ran a diagnostic harness against the shipped build on real hardware (v0.11.0, Win11 Pro 10.0.26300, Windows Terminal 1.24.12741.0) and the direct-child case is now measured: `CREATE_NO_WINDOW` + plain `cmd` → **0/3 visible windows**, no flag + plain `cmd` → **3/3 visible `CASCADIA_HOSTING_WINDOW_CLASS`**. That is the observation PR #36 (`f8450d42`) recorded as owed, and for the direct child it has been paid. What the census still proves and nothing more: **no site bypasses the owner.** What the hardware run additionally proves: **the flag suppresses the direct child's window.** What it **refutes**: that the flag reaches an **allocating descendant** — #156's §3 ran `CREATE_NO_WINDOW` against one (`CNW + start "" cmd /c`, and `start` without `/b` passes `CREATE_NEW_CONSOLE` by design, so that IS the tree case) and got **3/3 visible windows**; the hide-the-window family fails on the same split independently (`STARTF_USESHOWWINDOW`+`SW_HIDE`: direct child **0/3**, allocating descendant **3/3**). **Corrected 2026-11-06:** this bullet used to assert that the harness had never exercised this flag against an allocating descendant, and graded that case as unmeasured rather than refuted — it was run, and it lost. What the census and the hardware run still do NOT cover is the **packaged release bundle** under a window oracle of its own. The refutation does not demote the flag: it is still doing 100% of the work for every direct spawn, and no site may drop it. The lint's own scope statement is unchanged and must stay readable exactly as written above.
- **Scanned region is production code only** — the text before each file's `#[cfg(test)]`, the same boundary the `hostenv`/`sandbox` seams already lean on. Test fixtures keep building raw `Command`s; a fixture that needs the policy opts in explicitly.
- **`creation_flags` REPLACES rather than ORs** (rust-lang/rust#96794 again). Putting the flag inside the constructor makes that survivable: a site wanting `CREATE_SUSPENDED` or `CREATE_NEW_PROCESS_GROUP` later has no `Command` to set it on except one that came from `childproc`, so the flags have to be composed there. That is the real structural win, beyond the window bug.
- **`closed_stdin` is a separate, opt-in decision, not part of the constructor**, because it is wrong for every **Runtime child**: the Worker's JSONL stdin, the MCP server's JSON-RPC stdin and `sudo_exec`'s password stdin are pipes we actively write, and nulling one is a worse bug than the one being fixed. So the module cannot be "one call does the whole policy" — the **Tool child** / **Runtime child** split is the API, and the census test asserts both halves.
- **Two GUI-subsystem spawn sites get the flag for a reason that looks like a mistake.** The `--worker` self-exec and the updater relaunch run our own exe, which in release is GUI-subsystem, where `CREATE_NO_WINDOW` is documented as ignored — so they never popped a window. They still go through the constructor, because in a *debug* build the exe is console-subsystem and the flag is live there, and because a site added later inherits the correct default. A reader who notices should find this paragraph rather than "simplify" the call away.

## Amendment (2026-10-23) — the seam also owns the `cmd.exe` command-line tail (#79)

The module's remit widened from "the creation flags" to **every Windows-specific extension on a child `Command`**. The reason is not tidiness: `raw_arg` — the only stable way to hand `cmd.exe` a command line the way it is written — arrives on the same `std::os::windows::process::CommandExt` trait as `creation_flags`. A call site given one has the same one-line `use` that makes the other compile, and this ADR's whole premise is that `creation_flags` REPLACES rather than ORs with no getter to detect it (rust-lang/rust#96794). So `cmd_c_tail(command)` (the pure `/d /s /c "<command>"` formatter) and `append_cmd_c(&mut Command, &str)` (its `raw_arg` application) live here, next to `hide`/`hide_tokio`, for exactly the reason the flag does: composing the platform-specific parts of a child has one legal place.

The census gained **invariant E** for that: no production line outside `agent/childproc.rs` may contain `.raw_arg(`, anchored on the call form as invariant B anchors `.creation_flags(`, with a one-caller vacuity guard requiring exactly one `childproc::append_cmd_c(` outside the module (`exec/bash.rs`) so the check cannot pass for blindness. It guards production regions only, inheriting this ADR's existing scope rule that test fixtures build raw `Command`s on purpose. **Both file addresses in that paragraph are as-authored and are no longer paths in this checkout:** `childproc`, the `exec` tool and its `bash.rs` left this repo for the `fulcrum-core` crate (a rev-pinned git dependency), where the module is `src/childproc.rs` and the caller is `src/tools/exec/bash.rs`. The invariant and its one-caller count are unchanged; only the addresses moved.

The ADR's central honesty claim is UNCHANGED. E is a LINT on text: it proves no site bypasses the module that owns the `CommandExt` trait, and it does NOT prove the bytes `cmd.exe` received are correct — std renders the command line inside `CreateProcess` and exposes no getter, so that half is still owed what this ADR always owed it: one manual run of the packaged Windows build, plus the two `#[cfg(windows)]` `cmd.exe` tests in `agent/tools/exec/tests/bash.rs` — a desktop path that has since left this checkout for the `fulcrum-core` crate, where those tests sit in `src/tools/exec/tests/bash.rs` — which execute only on CI's `windows-latest` leg.

**Amended 2026-11-06 — what that "still owed" list has narrowed to, now that the direct-child run has happened.** Issue #156's harness ran the shipped build on real hardware (v0.11.0, Win11 Pro 10.0.26300, Windows Terminal 1.24.12741.0) and settled the *window* half for the direct child: `CREATE_NO_WINDOW` + plain `cmd` → **0/3 visible windows**, no flag + plain `cmd` → **3/3 visible `CASCADIA_HOSTING_WINDOW_CLASS`** (PR #36 / `f8450d42` is the durable handle for the decision that put the flag there in the first place). So the list above is no longer one undifferentiated debt. **Corrected 2026-11-06, second pass: this amendment previously counted three debts and put the allocating-descendant case first. That was wrong — that item is ANSWERED, and the answer is that the flag does not reach.** #156's §3 ran `CREATE_NO_WINDOW` against an allocating descendant (`CNW + start "" cmd /c`; `start` without `/b` passes `CREATE_NEW_CONSOLE` by design, so that run IS the tree case) and measured **3/3 visible windows**. Two items remain owed, and they are different debts: **(1) the packaged release bundle** — the `release.yml` artifact under a window oracle of its own has still never been run, and this is the only run that speaks to what ships; **(2) the `cmd.exe` bytes** — this paragraph's original point, untouched by any of it: `cmd_c_tail` / `append_cmd_c` render the command line inside `CreateProcess` with no getter, so proving the bytes `cmd.exe` actually received is still owed the packaged run plus those two `#[cfg(windows)]` tests on CI's `windows-latest` leg. **What the resolved item costs, since it is the reason it is no longer a debt:** the cheap lever class is exhausted for descendants — creation flags and the hide-the-window `STARTUPINFO` fields are both refuted there — so suppression at the root moves from candidate to **required** (`STARTUPINFO.lpDesktop` for a hidden desktop, or ConPTY via `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE`), and reaping via `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` is confirmed as fixing **lingering, never appearing**. That is a crate-side follow-up, not a fifth experiment. `start`'s own invocation shapes stay a live question, but they are a question about our instruction surface, not a debt of this amendment — see §2 of the research doc for the title-slot rule, which is what actually produced the reporter's windows. What is NOT owed and must not be re-opened: the flag's value for the direct child (**0/3**, measured) — the refutation bounds its reach, it does not remove the flag from any site. **One trap while chasing item (2):** a captured command line is not a discriminator between emitters. The `/d /s /c "<exact string>"` tail is OURS by design, and the double-space `cmd  /c` shape is what `cmd.exe` itself writes for its own children — so seeing either in a captured line proves nothing about whether some other, unflagged site built the `Command`. The census, not the captured text, is what answers "who built this". Note also, from the same harness, that a **naive window oracle is not evidence**: `start /min` produces a minimized `ConsoleWindowClass` window **3/3** that an `IsWindowVisible`-plus-on-screen-rect check silently misses, and **Windows Terminal REUSES its host process, so any probe that counts host processes passes vacuously — count new HWNDs.** A future run of item (1) must be built on HWND counting or it will report a green it did not measure.
