# The Session list's command strip is the app's view switcher — every view has exactly two exits and neither is a Back button

The **Session list**'s command strip used to be a row of three commands (Skills, Agents, Tasks) while the app's one navigation control, the Settings gear, sat at the far right of the chrome bar inside `ChromeControls`. We decided to move the gear into the strip — Skills · Agents · **Settings** · Tasks — and to delete `ChromeControls` outright rather than leave it holding zero buttons, so that the strip becomes the single surface that says which view is up and takes you to any other one. And we decided the corollary that makes this surprising rather than cosmetic: **there is no `Back` button anywhere in the app.** Both of them (`SettingsPage`'s and `TasksBoard`'s) are deleted, because once the strip is the switcher each view already has two exits — its own door, clicked again — and any **Session** row.

**Why the two exits and not one.** A door that only opens is how you get a dead-end view: the Settings page used to be exitable *only* by `Back`, because the gear sat in the chrome bar's `view === "settings" ? … : …` ternary's **else** arm and so was not even rendered on the view it opened. That is the failure this decision is really about. Now exactly one of {workspace, Settings, Tasks} is pressed at all times, the pressed door is the way out, and a row click is a second, independent exit — so no view can be entered without a visible route back, and no view needs an exit control of its own. **This reverses ADR 0094's D8** (a row click left Settings open), and the reversal is the point of the pair: 0094 made the pane permanent, which made it a *peer* of the content column; this makes it the *switcher*, which makes a row click mean "show me this Session" — including its view.

**Why `aria-pressed` is on two of the four buttons and deliberately NOT on the other two.** Skills and Agents raise **modals**; Settings and Tasks name **views**. A modal is not a location, so a pressed modal button would make "where am I" ambiguous — pressed would have to mean "a dialog is open", which is a different fact from "this is the view", and the strip would be carrying both. So Skills and Agents carry no `aria-pressed` and no pressed fill, and the two view doors carry `aria-pressed` plus the same `bg-selected` the active **Session** row wears, so "pressed" is one idiom in the pane rather than two. `App.test.tsx` pins all four buttons, so adding `aria-pressed` to a modal command reddens a test instead of quietly blurring the distinction.

**Considered Options**

- **Keep the gear in the chrome bar, add the sidebar door beside it** (a two-home migration, cheaper per commit): rejected — and not for taste. `getByRole` **throws** on multiple matches, and twelve `App.test.tsx` sites ask for the Settings button by name, so a commit that adds the door while the gear still exists reddens all twelve at once. The door therefore has to *move* in one commit rather than be added and then removed. That is an ordinary testing-library rule doing the work of a design argument, and it is worth recording because it makes an obviously-incremental refactor impossible: any future "let's just add it here first" hits the same wall.
- **Keep `Back` as well** (belt and braces, three exits per view): rejected — with a visible pressed door in a permanent pane, `Back` is a second answer to the same question, and the two disagree about where you came *from*. It also keeps alive a name (`onBack`) whose whole suggestion is "there is a place behind you", in an app that has decided navigation is forward-only: you leave a view by clicking where you want to go.
- **Delete `SettingsPage`'s `onBack` prop along with its button** (the obvious tidy-up): rejected — **it is not a button handler.** `SessionsSection`'s Reopen Space action calls it as the third step of `addSpace → openSession → onBack()`, so deleting it would silently break the landing on the tab the user just re-opened. It survives renamed to `onReturnToWorkspace`, which keeps the second consumer and stops the old name inviting a new Back button.
- **Empty `ChromeControls` instead of deleting it** (keep the cluster, remove its one button): rejected — an "app-control cluster" with no app control in it is a fiction, and the file's own doc-comment exists to explain a two-cluster grammar that would then describe one cluster of window furniture. The name goes with its last member.
- **Make Settings a peer in the Space tab strip** (it is a view, so put it with the other views): rejected — this is ADR 0094's D6, **re-affirmed, not overlooked**. Settings still hides `SpaceTabs` and spans the logo segment full width. The tab strip names **Spaces**; Settings is not one, and putting it there would make the strip answer two different questions in one row of tabs.

**Consequences**

- **The top-right corner of the window belongs to the window manager alone.** `WindowControls` is the chrome bar's last child and its only button cluster; nothing sits to its left any more. That is the fact a reader is most likely to trip over, since the corner used to hold app controls in two successive generations.
- **`CHROME_BUTTON` survives and its rationale does not.** The constant existed because *two* clusters shared a grammar; there is now one consumer (`WindowControls`). The constants stay — `chromeButton.test.ts` pins them byte-identical to the strings the buttons carried before the extraction, and its source gate requires `chromeButton.ts` to be the only production file under `src/components/` carrying the chrome-bar geometry — but the two-cluster story around them is now history, and the prose says so rather than naming a deleted component as a live consumer.
- **The sidebar door must NOT take the chrome grammar.** `PANE_COMMAND_ROW` is `h-8 w-full`; copying `CHROME_BUTTON` onto a pane button would redden that same source gate. A future reader adding a fifth command should copy the Tasks recipe, not the window controls.
- **A row click now leaves the view**, so the **Task board** and Settings are one click from any Session. One consequence is cosmetic and intended: rows are not marked active while a peer view is pressed (nothing is "where you are" while a door is), which also dims the row's status mark, since that mark takes brighter ink on the active row.
- **ADR 0094's D8 is reversed by amendment, not by editing.** ADRs are history; 0094's Consequences carries a dated amendment naming the reversal and why its own reasoning stopped applying.
- **`ADR 0038`'s exemption is unchanged and still asserted.** The exempted surface is the window controls only (`[data-window-control]`); the Settings door moved into the Session list and stayed *outside* it, because opening Settings is a person coming back to work. The property now holds structurally — the door is nowhere near the window controls — and is pinned anyway, because an unasserted structural property is one refactor away from regressing silently.
- **The `Back` deletion is only safe because 0094 landed first.** Before the hoist, the gear was absent on the Settings view and `Back` was its only exit. Anyone re-ordering this work must keep that dependency: delete the exits after installing the new ones, not before.

**Citing the code.** The implementation is two serial commits on `feature/kanban-task-board` — the strip/door move with `ChromeControls` deleted, then the two `Back` buttons and the `onBack` → `onReturnToWorkspace` rename — followed by this docs commit. **The per-task hashes are NOT the durable citation.** This repo squash-merges, so each becomes unreachable the moment the branch is deleted (`AGENTS.md`'s squash-orphan bullet measures 17 such hashes already stranded in `docs/`), and no PR number is citable from here: at authoring time the branch is unmerged and `gh` is unauthenticated in this environment, so the number cannot be read. **The durable handle is the squash commit (or the PR number) that lands this branch.** Where a hash would otherwise be load-bearing, the text is quoted verbatim above instead — the deleted component's name, the twelve `getByRole` sites, the `addSpace → openSession → onBack()` recipe, `PANE_COMMAND_ROW`'s `h-8 w-full` and the byte-identical-constant rule all stand on their own without a reachable object.
