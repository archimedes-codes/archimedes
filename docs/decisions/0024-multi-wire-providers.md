# Multi-wire model providers (Anthropic + OpenAI Responses) and a known-providers picker

The native harness spoke **OpenAI-compatible chat-completions only** (ADR 0012's "v1 is OpenAI-compatible only") and every user provider was ASSUMED OpenAI-compatible (ADR 0014). We decided: the harness speaks **three wire APIs** — `openai-completions` (the existing `OpenAiCompatibleProvider`), `anthropic-messages` (a new `AnthropicProvider`), and `openai-responses` (a new `OpenAiResponsesProvider`) — selected per model via the `Model.api` discriminator the catalog already carried, and the Settings' **Providers section gains a known-providers picker**: a built-in catalog of provider templates (name, base URL, wire API, key-management URL) the user can add as a **pre-filled provider row** with one click (the user still pastes the API key).

**Why:** the desktop's only model source is the user's provider list (ADR 0014), and adding a provider meant hand-typing a base URL — error-prone, and a dead end for the large providers whose best endpoints are NOT OpenAI-compatible (Anthropic, xAI, OpenRouter, the Chinese GLM/Kimi/MiniMax/DeepSeek/Bailian endpoints). The templates are seeded from the ZCode builtin provider catalog (`config/provider/zcode-builtin.json` — 20 user-facing templates). The picker does NOT bypass ADR 0014: a picked template becomes a normal `settings.json` provider row (the user's list remains the sole model source; the base catalog stays empty).

**Considered Options**

- **Pre-seed the provider list on first run** (every known provider as a keyless row): rejected — a keyless row whose endpoint needs a key shows `unreachable` / 0 models; the first-run screen would be a wall of failed rows. Opt-in per provider keeps the list the user actually uses.
- **Seed the base catalog with static models**: rejected — contradicts ADR 0014's "the user list is the sole model source" (the base catalog is empty by design) and the base catalog has no key storage, so the user would still add a provider row for the key — the static models would be dead weight.
- **A frontend-only known-providers constant** (no Rust involvement): rejected — the wire API is a harness concern (the `Provider` factory dispatches on `Model.api`), and the picker's pre-fill value (`api`) must match the harness's vocabulary; a Rust-owned catalog with a Tauri command keeps one source of truth.
- **Port the `anthropic-messages` wire from ZCode's TS adapters**: rejected — ZCode's adapters are a Vercel-AI-SDK TS stack; the harness is Rust and already owns its SSE parsing. The wire contracts are re-implemented natively (the `Provider` trait seam exists for exactly this, ADR 0012's "a second provider (Anthropic) can be added later without touching the loop").
- **One generic "adapter" with a protocol table**: rejected — the three wires differ structurally (Anthropic's `event:`-tagged SSE + `system`-as-top-level-param + alternating-role messages; Responses' `input`/`instructions` + `output` items) more than a table can express; three small, well-tested providers beat one giant switch.

**Consequences**

- **`ProviderConfig` gains `api`** (`"openai-completions"` (default) / `"anthropic-messages"` / `"openai-responses"`) + an optional `keyUrl` (set by the picker; a "Get key" link in the row). `#[serde(default)]` — a pre-feature `settings.json` parses to the OpenAI-compatible default (no migration). Discovered models carry the provider's `api` (no longer hard-coded `openai-completions`).
- **The selectable set generalizes** — `ModelCatalog::openai_compatible()` becomes `selectable()`: `supports_tools` + `api` ∈ the three supported wires (a `None`/unknown `api` stays unselectable, as before).
- **`ProviderFactory` dispatches on `Model.api`** (the `AgentLoop` is untouched — the seam ADR 0012 designed for).
- **Discovery is per-wire** — `openai-completions` / `openai-responses` keep the OpenAI `GET {base}/models` shape; `anthropic-messages` uses Anthropic's `GET {base}/models` (an id-only list — a discovered Anthropic model gets the `DEFAULT_CONTEXT_WINDOW` fallback and advertises no thinking levels; v1 does not fetch per-model metadata from Anthropic).
- **Thinking levels map per-wire** — `openai-completions` passes `reasoning_effort` through (today's behavior); `openai-responses` sends `reasoning: { effort }`; `anthropic-messages` maps the desktop's level vocabulary to a `thinking` budget (`low` 4096 / `medium` 10000 / `high` 20000 / `xhigh` 40000 / `max` 128000; an unrecognized level → `adaptive`), and the request's `max_tokens` is clamped above the budget (Anthropic requires `max_tokens` — a `None` option defaults to 32768).
- **The known-providers catalog is a Rust constant** (20 ZCode templates) exposed via a stateless `list_known_providers` command (the `list_tools` pattern); the picker pre-fills `name` / `baseUrl` / `api` / `keyUrl` and an empty key.
- **A user provider's models are NO LONGER assumed OpenAI-compatible** (ADR 0014's consequence updated) — the provider row's `api` decides the wire.

## Amendment (2026-10-29) — model and provider are a pair; AgentLoop rebuilds provider on model switch (#120)

**AMENDED 2026-10-29 — the claim that `AgentLoop` is untouched is contradicted and overtaken by #120.** What stands unchanged: the three wire APIs (`openai-completions`, `anthropic-messages`, `openai-responses`), the known-providers picker and its pre-filled rows, discovery per wire, thinking-level mappings, and ADR 0014's sole-model-source ruling. This ADR is NOT superseded and its `status` is unchanged. The sentence above in Consequences — **`- **`ProviderFactory` dispatches on `Model.api`** (the `AgentLoop` is untouched — the seam ADR 0012 designed for).`** — is deliberately left standing exactly as written, preserving the original design intent. The correction is recorded here.

**What changed.** `AgentLoop` is touched now: `model` and `provider` are an invariant pair (`AgentLoop` in `src-tauri/src/agent/harness/loop.rs`), built together at spawn (`default_build_loop` in `src-tauri/src/agent/worker/core.rs`). Any code that replaces the model must rebuild the provider from that same `Model` (`AgentLoop::set_model` in `src-tauri/src/agent/harness/loop.rs`). When mid-session model switching was added, `AgentLoop` was modified to update `self.model` without rebuilding `self.provider`, silently preserving the previous provider instance across a switch to a different model (issue #120).

**Why rebuild is keyed on the composed key rather than unconditional.** A live model switch changes the composed `"<provider>/<id>"` key, requiring a fresh provider instance built for that model. However, the rebuild must NOT run unconditionally on every model update: `SessionManager::refresh_live_models` (`src-tauri/src/agent/session/mod.rs`) pushes same-key metadata-only updates to update `context_window` and thinking levels without altering endpoint credentials. Unconditionally recreating the provider on metadata pushes would reset per-instance state, such as `accepts_stream_options` (`OpenAiCompatibleProvider` in `src-tauri/src/agent/harness/provider/openai.rs`), which latches after discovering a proxy rejects `stream_options`.

**ADR 0014's sole-model-source ruling stands intact.** The Settings list remains the sole model source (ADR 0014 — "The desktop has ONE model source — the Settings list"). The provider instance in `AgentLoop` is a view of a user's Settings provider rebuilt from the catalog's `Model` — never an independent per-session provider and never a second model source.

**Session persistence on model switch.** A mid-session model switch also persists the new model key and re-synthesised capabilities (`thinkingLevel`) to the session's database row (`SessionManager::set_config_option` (in `src-tauri/src/agent/session/mod.rs`) via `Db::update_session_capabilities` (`src-tauri/src/storage/db.rs`)), ensuring the switch survives app restarts.

## Amendment (2026-11-16) — `max_tokens` became an output ceiling and the thinking budget is what moves (fulcrum#26)

**AMENDED 2026-11-16 — one clause of the thinking-levels Consequence is false of the code shipped today.** The clause in Consequences above — **"and the request's `max_tokens` is clamped above the budget (Anthropic requires `max_tokens` — a `None` option defaults to 32768)"** — is deliberately left standing exactly as written, preserving what was decided on 2026-10-06. Both halves of it are now untrue: `max_tokens` is not clamped *above* a budget (it is a **ceiling**, and the budget is clamped *down* beneath it), and there is no `None` default of 32768 — the constant that carried it, `pub const ANTHROPIC_DEFAULT_MAX_TOKENS: u32 = 32768`, **no longer exists**. **This does not change this ADR's decision.** The multi-wire design stands in every particular: the three wire APIs, the `Model.api` discriminator, the known-providers picker and its pre-filled rows, discovery per wire, and the per-wire thinking-level mapping. What changed is the arithmetic inside one wire's request body. `status` is unchanged and this ADR is not superseded.

**What replaced it.** In `fulcrum-harness` 0.3.2 (engine PR `archimedes-codes/fulcrum#26`, desktop pin `152419dd`, i.e. `fulcrum-harness = "0.3.2"` in `src-tauri/Cargo.toml`) the one public constant became **three private constants** in the Anthropic wire builder:

| constant | value | role |
|---|---|---|
| `ANTHROPIC_OUTPUT_CEILING_TOKENS` | **64,000** | the CEILING on `max_tokens` |
| `MIN_ANSWER_TOKENS` | **16,384** | the floor left for visible text **plus the whole `tool_use` block** once a budget has been clamped |
| `MIN_THINKING_BUDGET_TOKENS` | **1,024** | Anthropic's own minimum legal `budget_tokens`, used as a **DROP THRESHOLD, not a floor** |

`max_tokens` is still always present — that half of the original sentence was right, Anthropic requires it — and a request carrying no caller cap gets the ceiling. The clamp then runs the other way: `clamp_thinking_budget` shrinks the **budget** to the room the ceiling leaves, 64,000 − 16,384 = **47,616**, and `anthropic_output_budget` writes the ceiling as `max_tokens`. That is the inverse of the `max_tokens.max(budget + 1024)` shape this replaced, which grew the request with the budget — exactly what Anthropic rejects. A caller cap is still **honoured, never raised to the ceiling** (the desktop's titling request sends `Some(100)`; the summariser sends anything in `1..=8_192`), because that arm's own cap *is* the answer room; the ceiling is the no-cap arm. The shape is pinned by three tests: `anthropic_request_body_max_tokens_is_a_ceiling_not_a_budget_sum`, `the_wire_never_asks_for_more_than_the_ceiling_and_always_outranks_its_budget`, and `the_clamp_shrinks_and_only_drops_when_no_legal_budget_fits`.

**The level table is unchanged.** `anthropic_thinking` still maps `low` 4096 / `medium` 10000 / `high` 20000 / `xhigh` 40000 / `max` 128000, and an unrecognised level still yields the `adaptive` mode with no budget. Only what reaches the **wire** changed: at `max` the table says 128000 and the wire sends **47616**. `low`/`medium`/`high`/`xhigh` all sit under 47,616 and keep their budgets **untouched** — `xhigh` still sends `budget_tokens: 40000`, so the ceiling costs that level nothing. `max` is the only level that shrinks, and what it used to send was not a silent clamp either: `128000 + 1024 = 129024`, which Anthropic answers with a **400**. Anthropic's own synchronous ceiling is 128,000 on current models and 64,000 on the 4.5 generation, and an over-cap value is a rejection rather than a truncation, so the ceiling sits at the conservative end of that range — the only end that cannot 400 — and a gateway with a *lower* cap silently clamps down instead of rejecting, which is what makes asking for 64,000 safe behind one.

**The Claude-family prefix gate is deliberately absent.** The ceiling is requested on this wire whatever the model id says. The family predicate (`is_claude_model`) gates prompt caching and nothing else, and gating the ceiling on it would **silently disable the ceiling for LiteLLM-routed Claude traffic**, whose id carries an alias prefix — routing changes what the far end will accept, so the prefix identifies the family and not the ceiling that applies to it.

**Why the ceiling is free on this wire and not on OpenAI's.** Per the engine's own rationale, recorded in `ANTHROPIC_OUTPUT_CEILING_TOKENS`'s doc comment: Anthropic documents that `max_tokens` does **not** factor into OTPM rate-limit evaluation (OTPM is assessed in real time on tokens actually generated) and bills output on the tokens generated, not on the cap requested — so the ask spends none of the bucket a smaller cap would have reserved. On the OpenAI side the same field is **not** free: its rate limit is the max of `max_tokens` and the estimated prompt size, and a LiteLLM gateway doing budget reservation estimates from the value. That asymmetry is why the OpenAI builders still **omit** the field when it is `None` (`openai.rs` writes `max_tokens` only under `if let Some(m)`, `responses.rs` writes `max_output_tokens` only under `if let Some(m)`), and it is why the ceiling is **Anthropic-wire-only**.

**The drop arm exists and is unreachable.** `MIN_THINKING_BUDGET_TOKENS` has exactly one job: when the room the ceiling leaves after `MIN_ANSWER_TOKENS` falls under 1,024 — i.e. a ceiling below 17,408 — there is no legal budget at all and `thinking` is **omitted** rather than emitting a `budget_tokens` the API would 400. It never *raises* a budget toward 1,024 (`room.max(1024)` would be dead code with a trap in it: it lifts the room to exactly 1,024 at any ceiling under 17,408 and, at a ceiling of 1,024 or lower, emits `budget_tokens >= max_tokens`). At today's 64,000 the drop arm is unreachable from every input; it is implemented because it is the clause that keeps the shape legal once per-model ceilings land.

**The live route is unaffected — this is not a live-behaviour change.** This deployment derives `openai-completions`: `route_hint_of("Qwen/…")` is `"qwen"`, which is not in `CLAUDE_ROUTE_HINTS` (`anthropic`, `bedrock`, `vertex_ai`), so `derive_wire_for_route` falls through to `WireApi::OpenAiCompletions`; the Messages rung is unreachable for this model regardless. And both OpenAI builders omit the field when `max_tokens` is `None`, so the live implicit cap is the gateway's — measured at 131,072. **The clamp this replaces was a genuine defect on a wire this deployment does not currently use**, and correcting it is not a no-op either. Nothing here touches the failure actually occurring on the live route (reasoning saturating the budget and returning an honest `stop` with zero visible text), which no cap sizing addresses.

**Provenance caveat on 16,384.** The floor's size rests on a live-tokenizer measurement over real DB traffic (62% of final reports, 65% of writes exceed 1,024 tokens) that is **not recorded in either repo** — the engine's own comment on `MIN_ANSWER_TOKENS` carries those two percentages as the only surviving copy of them and labels them REPORTED, not reproducible. 16,384 is the smallest power of two clearing both while still leaving more room than `xhigh` spends. If that measurement is ever re-taken and disagrees, `MIN_ANSWER_TOKENS` is the number to re-open — not the shape of the ceiling/clamp design.

**Follow-up recorded here, deliberately NOT done in this amendment (PENDING).** `docs/decisions/0108-a-length-stop-is-terminal-and-never-retried.md` carries a related now-false aside in its Consequences: it names as "the actual cause at this deployment's configured level" the fact that "the Anthropic clamp leaves ~1,024 tokens for the visible reply *and* the whole `tool_use` block at `xhigh`". That figure described the **old** `budget + 1024` clamp — at `xhigh` the old wire sent 41,024 against a 40,000 budget, leaving exactly 1,024 for the entire deliverable. **At `xhigh` the budget is now untouched at 40,000 and the answer's floor is 16,384**, so the sentence no longer describes any shipped arithmetic and needs its own amendment. ADR 0108's **decision is unaffected**: a length stop stays terminal and is never retried, because this change sizes the cap once at request-build time and does not re-issue on a `Length` stop — it neither adds a retry nor removes one. 0108 is **not edited here**; that session holds uncommitted work in it.
