# Every agent shell command opens a visible CMD window on Windows

Research question: *Why does the shipped Windows build pop a new console window each time the agent runs a command, what is the exact Win32 mechanism, and what is the correct lever?*

Filed as an issue against `danielcherubini/archimedes`. Symptom reported by a user: several blank Windows Terminal windows titled `C:\WINDOWS\system32\cmd.exe` stacking up during a session. **That sentence is the report of record — what the reporter saw — and it stays. What it was wrong about is the DIAGNOSTIC this doc built on it.** #156's harness measured that a blank window does **not** identify an unflagged spawn: a **fully flagged** direct spawn also produced blank windows (3/3), and their titles were **arbitrary `.cmd` path tokens**, not the `cmd.exe` exe path. The key that actually discriminates is `cmd`'s `start` title-slot rule, spelled out in §2 — not the title, and not the blankness.

## Executive summary

The app is a **GUI-subsystem** binary in release — the attribute is `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]`, at the top of `src-tauri/src/main.rs` — so its process has **no console to hand down**. Every child it spawns is a **console-subsystem** program (`cmd.exe`, `fd`, `rg`, an `npx.cmd` shim). Windows' documented rule is that a console child which is not "executed inside an existing console session" is **allocated a new console**, and "creating a new console results in a new console window". So: one `bash` tool call → one `cmd.exe` → one window.

**No spawn site in this crate sets a Windows creation flag.** `grep` over the whole repo for `creation_flags`, `CREATE_NO_WINDOW`, `DETACHED_PROCESS`, `STARTUPINFO` returns **0 hits**, and the app crate names no `windows`/`windows-sys`/`winapi` dependency at all. The lever that prevents it — `creation_flags(CREATE_NO_WINDOW)` (`0x0800_0000`) — exists on the exact `tokio` version we pin and has never been called.

*Read that paragraph as history, not as a live repo fact — it is the finding AS FILED against v0.3.0 (verified against `8cb499c`; see §Evidence), and the same disclaimer the §3 table carries applies to it. Every clause of it is false of this checkout: the flag IS set, in exactly one place — the crate's `childproc` constructor (PR #36 / `f8450d42`), which now lives in `fulcrum-core` — and the desktop keeps a guard of its own, `src-tauri/tests/childproc_census.rs`, whose invariant A fails the build if any desktop site builds a raw `Command` outside that owner (its invariants for `.creation_flags(` itself were deliberately not ported, because there are zero desktop sites for them — the crate's census owns that half). The §Gaps bullets above record the hardware run that observed the flag working (`CREATE_NO_WINDOW` + plain `cmd` → 0/3 visible windows). What still holds is the AS FILED diagnosis — the mechanism, the missing-lever shape of the bug, and the fact that no dependency would ever have set the child side for us — and the analysis underneath it is kept for exactly that reason.*

The windows are **blank** for a reason that is about our own piping, not about which site spawned them: `std` sets `STARTF_USESTDHANDLES` (we pipe stdout/stderr), so the new console's screen buffer is never substituted into the standard handles — the window is created *and* receives nothing. `STARTUPINFO.lpTitle` is NULL, so the title falls back to the executable name. **Corrected by #156's measurements:** blankness is NOT a discriminator between a flagged and an unflagged spawn — a fully flagged direct spawn was measured blank **3/3** as well — and the title the reporter saw is not reliably the exe path, because `cmd`'s `start` consumes a quoted first token as a TITLE and the window then carries that arbitrary `.cmd` path token instead. See §2 for the mechanism, which is the part that matters for triage.

This is the single most-reported Windows bug class in the Rust/Tauri agent-app ecosystem and is **never** closed as wontfix. Tauri's own `shell` plugin sets `CREATE_NO_WINDOW` on every command; **we do not use that plugin**, so we do not inherit its behaviour, and we reimplemented the spawn surface without the flag.

Two consequences for triage, both verified:
- **Invisible in `tauri dev`.** The subsystem attribute is `cfg_attr(not(debug_assertions), …)`, so a dev build owns a console and children simply inherit it. CI builds Windows in **debug** only — the `.github/workflows/ci.yml` matrix (`os: [ubuntu-latest, windows-latest, macos-latest]`) runs no release profile; `release.yml` is the only thing that ever produces the affected binary.
- **Every shipped Windows build is affected** — NSIS `Archimedes_x64-setup.exe`, v0.1.0 → v0.3.0, fresh installs and auto-updates alike.

## Findings

### 1. The rule that creates the window (Microsoft, primary)

| Claim | Source |
|---|---|
| A `IMAGE_SUBSYSTEM_WINDOWS_CUI` image *"will be allocated a console, unless it's executed inside an existing console session"*; GUI images are never allocated one and never block in a shell. | [Console Allocation Policy](https://learn.microsoft.com/en-us/windows/console/console-allocation-policy) |
| *"the system creates a new console when it starts the command processor `cmd.exe`"*; *"Creating a new console results in a new console window"*; *"GUI processes are not attached to a console when they are created."* | [Creation of a Console](https://learn.microsoft.com/en-us/windows/console/creation-of-a-console) |
| With `dwCreationFlags == 0`: *"The process inherits both the error mode of the caller and the parent's console."* | [`CreateProcessW`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) |
| `CREATE_NO_WINDOW 0x08000000` — *"The process is a console application that is being run without a console window."* Ignored for non-console children, and ignored with `CREATE_NEW_CONSOLE` or `DETACHED_PROCESS`. | [Process Creation Flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags) |
| `"console"` subsystem: *"If a console process is run from an existing console then it will be attached to that console; otherwise a new console window will be created."* | [Rust Reference — `windows_subsystem`](https://doc.rust-lang.org/reference/runtime.html) |

`std`'s default is the degenerate branch. `library/std/src/sys/process/windows.rs` initialises `Command { flags: 0, … }` and at spawn computes `let mut flags = self.flags | c::CREATE_UNICODE_ENVIRONMENT;` — i.e. **nothing** console-related is ever passed unless the caller opts in. `self.detach` would add `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` but is *"not currently exposed in std::process"*.

### 2. Why the window is blank — and why redirecting more streams cannot help

Console allocation is decided by image subsystem + `dwCreationFlags`, with **no handle condition anywhere** in the docs. Redirection therefore does not suppress it. What redirection does do is starve the window:

- `std` sets `STARTF_USESTDHANDLES` whenever any stdio stream is non-null (`si.dwFlags |= STARTF_USESTDHANDLES` in the same file — ours always is, we pipe stdout/stderr).
- [GetStdHandle](https://learn.microsoft.com/en-us/windows/console/getstdhandle): *"standard handles are always replaced with console handles **unless `STARTF_USESTDHANDLES` was specified** during process creation."* So our pipes stay, and the new console's buffer is never wired in.
- [STARTUPINFOW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-startupinfow): the screen-buffer default applies only when `STARTF_USESTDHANDLES` is absent; and a NULL `lpTitle` means *"the name of the executable file is used as the window title"*.

Net: an empty black/`cmd.exe`-titled window for the child's whole lifetime. The blankness is a *symptom of our own piping*, which is why it reads as "the window does nothing".

**Measured 2026-11-06 (issue #156's harness, v0.11.0, Win11 Pro 10.0.26300, Windows Terminal 1.24.12741.0): blankness does not discriminate, and the title the doc keyed on is usually not the exe path.** A **fully flagged** direct spawn — `CREATE_NO_WINDOW` set, our own construction path — was measured producing blank windows **3/3**, and their titles were **arbitrary `.cmd` path tokens**, not `C:\WINDOWS\system32\cmd.exe`. So neither "it's blank" nor "the title is the exe path" tells you whether a spawn was flagged. What actually produces the shape the reporter saw is **`cmd`'s `start` title-slot rule**, and it is a different bug from the one this doc is about:

- `start "<path>.cmd"` — with no empty title slot — consumes the **first quoted token as a TITLE**, launches a **bare `cmd.exe`**, and the target never runs: the harness recorded `target_actually_ran=False`. The window therefore **never closes**, because the thing that would have exited never started.
- `start "" "<path>.cmd"` — the empty title slot — is correct and was measured **windowless**.
- `start "<path>.cmd" --flag` is worse than cosmetic: the `--flag` is taken as the command, `cmd` raises a **`#32770` modal dialog**, and the **tool call blocks** — the harness recorded `child_alive=True` at 8 s. A hung tool call whose window is a dialog, not a console, is this shape, and no creation flag helps it.
- App-shaped aggravation, and the reason it shows up HERE: `start "\\?\D:\…"` behaves identically, and this app writes **`\\?\`-prefixed paths into `sessions.cwd`**. The extended-length prefix does not make the token safer as a title; it makes it more likely to be quoted, which is the condition the title-slot rule turns on.

Triage consequence, stated plainly so nobody re-derives it: a blank window is evidence of *our piping*, and a lingering window titled with a path is evidence to go look at the **`start` invocation shape**, not at the creation flags. The two are independent, and only the second one was ever a window-suppression failure.

**And one fingerprint that looks like evidence and is not.** The double-space shape `cmd  /c` in a captured command line is what **`cmd.exe` itself writes for its own children**, so seeing it is **not** evidence of an unflagged emitter in our code. Any triage that treats a captured command-line shape — `cmd  /c`, a single-shot `cmd /C <command>`, the `/d /s /c "<exact string>"` tail our own `childproc::cmd_c_tail`/`append_cmd_c` renders — as a discriminator between "our spawn" and "someone else's" is reading `cmd`'s own quoting back to us as an accusation. The discriminators that do work are the ones above (does the target actually run; is the window a console or a `#32770` dialog) and the ones below (count new HWNDs).

**Not every row is a window.** `CREATE_NO_WINDOW` is documented *"ignored if the application is not a console application"*, and the self-exec runs **the same exe** — which in release is `IMAGE_SUBSYSTEM_WINDOWS_GUI`. The two lines at the top of `src-tauri/src/main.rs` — the subsystem attribute itself, quoted below — are the only place in the entire repo, code, docs, tests, that acknowledges console windows at all:

```rust
// Prevents additional console window on Windows in release, DO NOT REMOVE!!
#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]
```

That attribute governs the **parent's own** console ([rust-lang/rust#90674](https://github.com/rust-lang/rust/issues/90674)). It was doing its job; nothing was ever done about the **children's**. `tauri-build` 2.7.2 and `tauri-winres` never set a subsystem — the attribute is user-authored template boilerplate, so no dependency will ever fix the child side for us.

`tokio::process::Command` **does** expose the lever: the pinned `tokio-1.53.1` has `pub fn creation_flags(&mut self, flags: u32)` inside `cfg_windows!` at `tokio/src/process/mod.rs:675`, delegating straight to `std`. It is a **setter, not an OR** — a later call by any wrapper silently clobbers it ([rust-lang/rust#96794](https://github.com/rust-lang/rust/issues/96794) tracks the missing `current_creation_flags`).

### 4. Frequency, and the second window source

One `bash` tool call is one window (the `#[cfg(not(unix))]` arm of the `exec` tool's spawn, reached from the harness's tool-execution step in the agent loop). MCP stdio clients spawn **once per server per session** (`manager.rs` memoises `ensure_connected`) but re-spawn after an exit or a turn-cancel, plus a fresh one per Settings → Test click, and every subagent dispatch owns its own `McpManager`. A `.cmd`/`.bat` shim is *itself* a `cmd.exe` invocation, so an `npx`-based MCP server can cost two windows per spawn. There is **no** `.cmd`/`.bat`/`PATHEXT` handling anywhere in `src-tauri/src` (grep: 0 hits).

The Rust idiom is a small `#[cfg(windows)]` helper — [Codex `background_command`](https://github.com/openai/codex/blob/main/codex-rs/utils/process/src/lib.rs#L11-L17), [Zed `crates/util/src/command.rs:38`](https://github.com/zed-industries/zed/blob/main/crates/util/src/command.rs#L38), [WezTerm `spawn-funcs`](https://github.com/wez/wezterm/blob/main/lua-api-crates/spawn-funcs/src/lib.rs#L41), [Lapce `dap.rs:172`](https://github.com/lapce/lapce/blob/master/lapce-proxy/src/plugin/dap.rs#L172). There is **no** maintained crate for this (`no_window_cmd` does not exist on crates.io — it is ~10 lines vendored by folklore into ~30 Tauri repos). Five other runtimes expose a *named* API for the same intent: Node `windowsHide`, CPython `STARTF_USESHOWWINDOW`+`SW_HIDE`, Go `SysProcAttr.HideWindow`, .NET `CreateNoWindow`. Hiding the child window is standard practice, not a hack.

**REFUTED as a fix on this stack (measured 2026-11-06 by issue #156's harness) — and the sentence above it is the claim that was wrong.** "Standard practice" is true of the *intent*; it is not true of the *sufficiency* of the hide-the-window family. `STARTF_USESHOWWINDOW` with `wShowWindow = SW_HIDE` suppresses the **DIRECT** child's window (**0/3**) but **not** an allocating descendant's (**3/3**) — **and `CREATE_NO_WINDOW` fails on that SAME split, on a measurement of its own.** #156's §3 ran the flag against an allocating descendant directly: `CREATE_NO_WINDOW` + `start "" cmd /c` → **3/3 visible Terminal windows**, and that IS the tree case, because `start` without `/b` passes `CREATE_NEW_CONSOLE` by design — the child allocates its own console, which is precisely the situation the flag was supposed to be tested in. So this paragraph now records **two independent refutations on the same split, one per lever**, and the flag's side of it is a direct observation, not an expectation borrowed from a neighbour (see §6 and the §Gaps bullet, which are corrected to say exactly that). **Corrected 2026-11-06, and the correction cuts both ways, so keep both halves:** the flag's reach into an allocating descendant is refuted, which does NOT make the flag useless — `CREATE_NO_WINDOW` + plain `cmd` → **0/3** stands, and the flag is still doing 100% of the work for every direct spawn. What is refuted is the **tree-wide** reach, not the flag. It is exactly why the §Gaps bullet is now closed for the direct child and **refuted** for the tree, rather than merely narrowed. `start /min` is the trap inside the trap: it yields a **minimized `ConsoleWindowClass` window 3/3**, and a naive oracle built on `IsWindowVisible` plus an on-screen-rect test **silently misses it** — the window exists, it is simply off the naive oracle's map. **Oracle warning, and it is the load-bearing one: Windows Terminal REUSES its host process, so any window-probe built on counting host PROCESSES passes vacuously — count new HWNDs.** A harness that concluded "no new conhost/WT process, therefore no window" measured nothing; every number quoted in this doc came from counting HWNDs.

### 6. Residual risks the fix must respect

- `CREATE_NO_WINDOW` gives a **windowless console**, not a console-less child. A child that calls `AllocConsole` still gets a window ([AllocConsole](https://learn.microsoft.com/en-us/windows/console/allocconsole)); `cmd /c start …` starts a new window regardless (`/b` is the documented no-window variant). **Sharpened by the 2026-11-06 measurements, and on THIS exact combination — measured, and the flag lost:** #156's §3 ran `CREATE_NO_WINDOW` against an allocating descendant (`CNW + start "" cmd /c`) and got **3/3 visible Terminal windows**, so the flag's reach into that case is **refuted by direct observation, not inferred from the neighbouring hide-the-window family** (`STARTF_USESHOWWINDOW`+`SW_HIDE`: direct child **0/3**, allocating descendant **3/3**) — that neighbour is now a SECOND, independent refutation on the same split rather than the only evidence for it. **Corrected 2026-11-06:** an earlier version of this bullet asserted that the harness had never exercised this flag against an allocating descendant, and graded the tree-wide case as unmeasured rather than refuted; that was false, and it collapsed two different measurements (§3's flag run and §4's `SW_HIDE` run) into one. **What that costs, stated plainly because it changes what to do next:** the cheap lever — a flag, or a hide-the-window `STARTUPINFO` field — is now **known not to work** on a descendant that allocates, so this is not a gap one more experiment closes. Suppression at the root moves from candidate to **required**: a hidden desktop via `STARTUPINFO.lpDesktop`, or ConPTY via `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE`. Reaping (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) is confirmed as fixing only **lingering**, never **appearing** — a job object kills the descendant that already made its window; it cannot unmake the window. **What is NOT refuted:** the flag's effect on the direct child (**0/3**, §5 and §Gaps) — for every direct spawn it is still doing 100% of the work, and nothing here argues for dropping it. And the standing advice in this bullet survives the correction intact: when a window survives a flagged spawn, audit the `start` invocation shape (the title-slot rule in §2) **before** you audit the flags.
- Do **not** reach for `DETACHED_PROCESS` instead: it suppresses `CREATE_NO_WINDOW` (documented ignore), and leaves the child free to `AllocConsole` later. `CREATE_NEW_PROCESS_GROUP` is orthogonal and disables CTRL+C group-wide via an implicit `SetConsoleCtrlHandler(NULL, TRUE)`.
- `creation_flags` is a **replace**, so a central helper must own it (Codex documents exactly this constraint in its own comment).
- A hidden child is an **invisible** child: anything waiting on stdin now deadlocks behind nothing. `exec_bash` currently leaves stdin *inherited*, so the confined tier and any interactive child need deciding alongside the flag.
- Reported in the wild (secondary source, low confidence): `CREATE_NO_WINDOW` under a **write-restricted token** can fail the child at loader init (`0xC0000142` `STATUS_DLL_INIT_FAILED`). Our confined tier **fails closed off-Linux** (the confinement arm of the `exec` tool, which returns a refusal rather than a spawn on any non-Linux host), so there is no Windows sandbox today for it to bite — but it becomes live the day Windows confinement lands.

- **NEW (2026-11-06, measured) — the biggest measured cost is not a window, it is the output-pipe deadline; the fix lives in the crate, so this entry is a POINTER.** Of **8,685** `bash` tool calls the harness observed, **1,418 (16.3%)** came back carrying the app's own sentence **"a background process still held the output pipe open"** — the deadline note the tool surface renders when a run finished cleanly but its pipes would not close (the sentence is crate-authored; quote it back when filing against the fulcrum repo). Hit rate by the shape that spawned it: `start /min` **26/26 = 100%**, `Start-Process` **9/10**, `start /b` **63%**, plain **15%**. Read the gradient, because it is the finding: the cost tracks the **emitter**, not the flag — every shape that detaches a descendant into the background inherits a held pipe, and `CREATE_NO_WINDOW` does not touch pipes. **This is the output-side twin of the inherited-stdin bug** this section already records as CLOSED: that one was a child reading stdin that would never arrive, this one is a parent reading output that will never end, and the crate reasons about both in `childproc`. **Ownership, stated so nobody hunts for the fix in this checkout:** the deadline logic is **crate** code — `fulcrum-core`, pinned by full rev in `src-tauri/Cargo.toml` (`fulcrum-core = { git = "https://github.com/archimedes-codes/fulcrum", rev = "78e595436ac5612d8ef87f692bee61f48f6e58e7" }`), where `src/tools/exec/bash.rs` declares `pub const DRAIN_GRACE: Duration = Duration::from_secs(2);` and the drain paths run in the crate's `src/interactive/sudo_exec.rs`. **Follow-up, owner `archimedes-codes/fulcrum`:** the drain/deadline policy itself. **What this repo DOES own here** is the advice the tool description gives the model: rate-limiting or re-shaping `start`-derived invocations (`start /min`, `start /b`, `Start-Process`) is user-side guidance and belongs in our docs and tool description; changing when we decide a run is over is crate territory. Both halves are named so neither is mistaken for the other.
- **FINDING (2026-11-06, no edit made) — the DESKTOP-side census shares the crate census's two understatements; the sharper of the two is currently LATENT here.** `src-tauri/tests/childproc_census.rs` re-derives the crate's scanner deliberately (the crate's `lint_scan` is `#[cfg(test)]`, and `#[cfg(test)]` does not survive into a dependency), and it inherits both shapes. **(1) A line-position boundary, not a module boundary:** its `production_boundary` is documented as *"the first line whose TRIMMED text STARTS WITH `#[cfg(test)]`"* and is implemented as a `position(…)` on that predicate — a line-position `break`, not bounded to a test MODULE, so a `#[cfg(test)]`-attributed `use` block sitting in item position truncates everything after it. **(2) A whole-directory exclusion:** its `is_test_target` returns an empty region for `**/tests.rs` and for anything under `/tests/`, which removes the `src/**/tests/*.rs` files under `src-tauri/src/agent/` entirely — the same confound the crate census carries. **The difference in exposure is the honest part of this finding:** the `#[cfg(test)] use …` import form is **LATENT** on this side — measured 0 live desktop sites, i.e. no file under `src-tauri/src` pairs an item-position `#[cfg(test)]` with a following `use` — and **LIVE** in the crate (the crate's `worker/manager/mod.rs` and `harness/loop.rs` both carry `#[cfg(test)] use` blocks). So the desktop census is not losing lines to that hatch today; it is one import away from losing them silently. **And the vacuity floors do not cover it:** this file's own floors (`walked >= 40`, `read_lines >= 6000`, `std_calls >= 1`) are floors on lines **read**, not on lines **excluded**, so adding a `use` above the real test module would redden nothing until the guard's own needle was threatened. The honest statement about the desktop census's scope is therefore *"at least its floor of lines, all of it above the first item-position `#[cfg(test)]`, some of it confounded by the `tests/` exclusion"* — not *"the whole desktop production region."* **Follow-up, census hardening** (crate `lint_scan` + this desktop census): make the boundary module-bounded instead of first-`#[cfg(test)]`-line-bounded, and teach it about `#[cfg(test)] use` import blocks. **No change was made to `src-tauri/tests/childproc_census.rs` on this pass** — it is source, and the correction recorded here is documentary.
