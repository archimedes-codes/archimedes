# Palettes

A **Palette** is the Client's colour-scheme axis — the persisted `palette` setting, applied as a single `.theme-<palette>-<mode>` class on `<html>` over the shared `.dark` token block. It is orthogonal to **Theme** (the light/dark mode): the Palette answers *which hues*, the Theme answers *how light or dark*. **Seven** Palettes ship — Default, Dracula, Everforest, Catppuccin, Ayu, Rosé Pine, Kanagawa, in that picker order — carrying **13 readings** between them (6 light, 7 dark). Whether a Palette follows the Theme mode is the Palette's own property: `dracula` publishes one reading and so PINS the app dark, `system` included, while the other six follow the mode. That is data (`modes` on each registry entry), not a branch — ADR 0104.

The **registry** (`src/lib/palettes.ts`) is the single app-side authority: id → label → `modes` → Shiki pair → class names. `PaletteId` is derived from the registry literal rather than written a second time, which matters because the Rust side stores `palette` as an unvalidated `Option<String>` and the frontend union is therefore the only place a typo can be caught at compile time. An id the registry does not name resolves to Default — the *measured* behaviour of the code the registry replaced, now explicit (ADR 0104).

Syntax highlighting is DERIVED from the Palette and its resolved mode (a registry lookup, never a third setting): **13 Shiki ids**, one `createHighlighter` holding all of them at both call sites (`AgentMarkdown`, `CodemodeCard`), loaded from `shikiThemesToLoad()` rather than a literal list. `main` loaded 2 (`github-dark`, `dracula`), so this plan added **11** — one more than the plan's own arithmetic predicted ("12": Default's pair plus five Palettes × 2), because that sum omitted Dracula's pre-existing `dracula` id, which is still in the list. Measured cost: ≈0.1 MB heap and ≈6 ms per theme, and **0 new bytes on disk** (all 65 Shiki theme chunks were already emitted into `dist/`). Dual-theme output (`themes: { light, dark }`) is deliberately NOT used — measured 1.45× HTML / 1.85× time at two themes, and the mode is already known at the call site.

**The gates grade every Palette, not one.** Five gates used to name Dracula literally; they now enumerate `src/lib/palettes/<id>.ts` — the per-Palette **spec-data** rows that carry each scheme's published hexes, ladder groups, allow-lists and contrast floors. Adding a Palette means adding a row and a CSS file, with no edit to any shared gate. ADR 0027 holds the axis decision and its amendments; ADR 0104 the per-mode reading and the rename; ADR 0105 the ladder and the alpha rule. **This doc records what the values cost, so a future palette author does not pay it twice.**

Plus the two shared base layers every Palette diffs over: `@theme` 185, `.dark` 149. **15 layers in total**, all brace-counted from the resolved `src/index.css`.

The light readings carry fewer declarations than their dark siblings by design, not by omission: a light block restates the surfaces and the inks, and inherits the identity-hue and ramp families that a light page already reads correctly from `@theme`. A missing declaration is not a failure in this class model — it silently inherits `@theme`, which is exactly why the completeness gate is a completeness gate rather than a spot check.

**Cascade order is not load-bearing between Palettes**, and the plan sentence that said it was is wrong. Every Palette block is a single-class selector of equal specificity, and `src/lib/theme.ts` guarantees at most one `.theme-*` class is ever present, so there is no tie for source order to break. `utilities.css` sits before the Palette blocks and declares no theme token, so its position decides nothing either. The two facts the cascade DOES depend on — `@theme` first, `.dark` before every Palette block — are pinned by name by `paletteCompleteness.test.ts`; the Palettes' mutual order is deliberately left unpinned.

## Where each Palette's own record lives

**Every Palette's block header in `src/styles/<id>.css` is its own authority** — its spec URL with a hash where the source is fetchable, its transcription hazards, its ladder with every hop's luminance, its measured contrast walls, and its deliberate departures stated plainly. That is deliberate: the record belongs beside the hexes it explains, and a second copy here would be a second thing to keep true. The five new headers run 198–307 lines each. What is recorded there and nowhere else:

- **Catppuccin** (`catppuccin.css`) — Mocha/Latte, six published neutrals per flavour; the seam property ADR 0096 was written from (Latte's recessed/island midpoint is itself a published step); why `surface0` is not a surface in either reading; that Latte's ladder runs the other way from every dark reading; the alpha classification; four departures.
- **Ayu** (`ayu.css`) — `dark.yaml`/`light.yaml` as authority, with the finding that **three different backgrounds exist and none of them is the code-block colour** (Shiki's normalised `bg` is `#0d1017` where the theme file says `#10141c` and the published spec says `#0B0E14`); ladder groups labelled in Ayu's own vocabulary; the float-on-slab collision Dracula buys, bought again.
- **Rosé Pine** (`rose-pine.css`) — `rosepinetheme.com/palette` plus the `rose-pine/palette` repo; `moon` deliberately not shipped (a second dark, and the registry has one slot per mode); ten recorded walls, four resting and six raised, most on the selection state `#403d52`; four departures.
- **Kanagawa** (`kanagawa.css`) — the README's Name/Hex/Usage table plus the two Lua sources, and the rule that **where the two disagree `themes.lua` is the authority**; the scheme's own published WCAG 2.1 AA clause quoted verbatim, and the structural reason that clause breaks on Lotus (light) rather than on Wave; four departures.
- **Everforest** (`everforest.css`) — `palette.md`, sha256-verified against the file it was transcribed from; the finding that the dark reading ships the `hard` contrast level when the spec calls `medium` the default, and the measurement that justifies it; the one sub-floor ladder hop, recorded as a concession rather than engineered away; the identity-hue census that parks the hue-rejecting steps off any plane a glyph rides.

`src/lib/palettes/<id>.ts` is the machine-readable twin of the same record: `publishedHexes`, `ladderGroups`, allow-lists, and the floor tables — each exemption carrying an `expiresAt` floor, so it dies the day the hue clears the bar rather than outliving its reason. 109 of those 110 pins sit at 4.5 (the text floor); the one exception is Catppuccin Latte's `color-foreground` at 6.5, pinned just under its measured 5.17→6.57 band so a re-hue that loses the margin fails by name.

## The Default palette's colours were NOT re-tuned, and that is a decision

The work this record came from was asked to "update the default theme", and a reading of that as "re-tune its colours" was on the table — the Default palette is 143 light + 168 dark declarations, and re-inking it is not mechanically hard. It was decided **not to**, on the ground that no target reading was ever agreed and inventing 143 hexes is not something a change may do to a user's default appearance as a side effect of adding other schemes. What shipped instead is the decidable part of the same request: the `zai` de-branding, the stale figures, and the one token that was provably broken (`--color-accent`, above).

Consequence for anyone tempted to do it later: every surface reading in that palette is load-bearing for the gates, so a re-hue is not a design pass but a re-derivation — all 25 Identity hues must stay ≥ 3:1 on the surfaces they ride and every graded text token ≥ 4.5:1 on its own page, in **both** readings, for **all seven** Palettes. `fileIconContrast.test.ts` and the per-Palette floor tables are what a re-hue has to satisfy, and the light half of the identity-hue gate is still ungraded (Open follow-ups), so a light re-hue could currently be shipped with no test noticing. Decide the surfaces first, then the floors.

## Two toolchain facts that generalize

- **Tailwind v4's scale is `oklch()`, so "copy the old hex" is never byte-identical.** The ramp tokens replace utilities like `text-blue-500` with literals that are Tailwind v3's *hex* for those colours. Decoding the real v4 `oklch()` and comparing: worst case on this branch is **0.0110 relative luminance / 0.19 contrast** against the surface the glyph paints on (orange, the context band; the five ramp hues are ≤0.0105 / ≤0.18) — sub-perceptual, all still clearing their floors, but "identical" is a claim about pixels and these are different pixels.
- **`lightningcss` emits a static approximation for any `color-mix()` containing `var()`, then the real rule behind an `@supports` guard.** The build artifact reads `--color-background-alt:#e5e5e599` followed by `@supports (color:color-mix(in lab, red, red)){…color-mix(in oklab, var(…) 60%, transparent)}`, so capable webviews get the true value. Grep the *source*, not `dist/`, when reasoning about a `color-mix` token.

## Adding a Palette

The registry plus the spec-data row is the whole contract, and the gates were refactored before any Palette beyond two existed so the fix would be provably load-bearing rather than speculative. Four gates passed a broken third Palette silently before that refactor, and each is now armed:

1. **The class invariant** used to filter over a hardcoded three-name array, so a fourth `.theme-*` class was invisible and two co-applied classes still satisfied "exactly one". It now sweeps `themeClassNames()`.
2. **Every value-grading assertion** used to iterate `DRACULA_VALUES`; they now iterate the spec rows discovered from `src/lib/palettes/`.
3. **`shikiThemeFor`** used to be a two-arm ternary, so a third Palette rendered `github-dark` code — `codeToHtml` asks for a theme the highlighter never loaded, throws, and the call site's `catch` renders the plain fallback, so the failure was invisible. Both `themes:` lists are now registry-derived and gated to cover the registry.
4. **The picker's save rule** used to name both values it knew, so a third selection wrote `"dracula"` into `settings.json` — a wrong value persisted by a green suite. It is one expression over the registry now, and the round-trip test covers all seven values.

The gates fail on the real omission before the code exists — that observation is what makes them gates. A new Palette needs: `src/styles/<id>.css` (dark and light blocks, with the header record), `src/lib/palettes/<id>.ts` (published hexes, ladder groups, allow-lists, floors with `expiresAt`), one registry entry, and one `@import` in `src/index.css`. No shared gate is edited, and no Rust changes — `palette` is an unvalidated `Option<String>` that nothing branches on.

**Do not "finish" the default Palette's rename in Rust.** The default Palette's former id and the Z.AI **model provider's** id were the same string. The provider catalog in `src-tauri/src/config.rs` (`id: "zai"`, `base_url: "https://api.z.ai/api/anthropic"`, and the `zai-api` sibling) is a live model endpoint, asserted in `commands/settings.rs`; a repo-wide find-and-replace would break model access while looking like a completed rename.

## Open follow-ups

*The list is axis-wide, not one scheme's TODO — only the Alucard entry is Dracula-specific.
It moved here from the Dracula section when that became a subsection of this record.*
- **`--color-accent` is legible as text in the Default palette's DARK reading and still sub-floor in its LIGHT one.** `SubagentDelegatingCard.tsx:438` renders the thinking level with `text-accent`, and that is the token's ONLY consumer in production. Both Default readings now carry `#bd93f9`: **dark 7.50 on the page (`#161616`) and 6.75 on the panel (`#202020`)**. Before that, dark carried `#001d3d` — **1.07** on the page, **1.04** on the panel — and light carried `#ebf4ff` at **1.11** on white, so the token was invisible in both readings; the `.dark` definition (a `color-mix` of sky-950) shows it had been written as a surface tint, not a text hue. **Light is now 2.27 on its own page (`#f8f8f8`) and 2.41 on white**, still under the 4.5 text floor, and no single hex can clear both: legible text on `#f8f8f8` needs luminance ≤ 0.170 while legible text on `#161616` needs ≥ 0.284, and `#bd93f9` is 0.385. **This is a gap the whole axis shares, not a Default defect** — each Palette's light `--color-accent` against its own page: rose-pine 1.06, catppuccin 2.17, default 2.27, ayu 2.65, everforest 3.13, kanagawa 3.72. All seven dark readings clear it, from kanagawa 6.41 to catppuccin 13.86. Fixing the light half means either two values for one token or moving the consumer off `text-accent`, and either is a decision about the token's role, not a value to look up.
- **`text-secondary-foreground` (`src/components/ui/badge.tsx:13`) names a token declared nowhere** — no `--color-secondary-foreground` in `src/index.css`, so Tailwind emits no utility. Pre-existing, unrelated to the palette.
- **Shiki's `langs` allowlist still omits `css`, `html`, `markdown` and `vue`.** `codeToHtml` THROWS on an absent language, the call site catches it, and the fence renders plain with no signal — so these are silently unhighlighted (`tsx`/`jsx` were added on this branch; `sql`/`go`/`svelte`/`diff`/`ini` likewise absent). The header stays correct either way, since it comes from `fileIconFor`, not Shiki. Widening the allowlist or moving to bundled grammars is the fix.
- **The identity-hue gate does not grade light surfaces at all — the silent-pass class this plan closed on the dark side is still open on the light side.** (The dark half used to be a hardcoded two-entry list graded exactly two Palettes; `fileIconContrast.test.ts` now derives its DARK table from the registry (`REGISTRY.filter(p => p.modes.includes("dark"))` over `BASELINE_SURFACES`), so a new Palette gets dark grading on day one.) Its LIGHT half is one hardcoded constant — `const LIGHT_BG = "#f8f8f8"`, `.theme-default-light`'s page — and the only light assertion is `it.each(names)("%s clears 3:1 on the LIGHT background")` over `BASE`, i.e. `@theme`'s 25 light-safe readings against that one hex. It has **no palette dimension whatsoever**: every Palette runs the identical 25 assertions against the identical hex, and `@theme`'s readings were chosen for exactly that page, so it is unfailable by construction (measured 0/25, worst ratio 3.4100 — kit `contrast`/`resolveToHex`, cascade built as `gradeReading` builds a light one: `@theme` + the block, no `.dark`). What the same 25 hues actually do on each Palette's OWN light planes, none of it graded: **Catppuccin Latte** `--color-panel` `#dce0e8` rejects **19/25** (worst `file-svelte` 2.7369) and `--color-background` `#e6e9ef` rejects 4/25; **Kanagawa Lotus** rejects **20/25** on `--color-background` `#dcd5ac` (worst 2.2741–2.4413), 19/25 on `--color-chat` `#e5ddb0` and 20/25 on `--color-panel` `#d5cea3`. Default, Ayu, Rosé Pine and Everforest read 0/25 on all three of their own `background`/`chat`/`panel`. Extending `BASELINE_SURFACES` to light readings would add 450 assertions (3 rendered planes × 25 hues × 6 light readings; Dracula ships no light reading) and **fail 82 of them today, on 5 rows — all Kanagawa Lotus and Catppuccin Latte.** That is why this is a recommendation and not a change: it reddens the suite, and `--color-panel` is a plane a glyph really rides (the code-block header in `MessageBubble.tsx`), so a red row there is a design decision about a surface, not a test to delete. Everforest's light reading is the model for what the fix looks like: it puts `--color-panel` on the `#fdf6e3` plateau precisely BECAUSE the header rides it, and parks the hue-rejecting steps (`#e6e2cc` 19/25, `#e0dcc7` 19/25) on `--color-frame` and the badge fills, with the census written into `src/styles/everforest.css`. Kanagawa Lotus and Catppuccin Latte carry no such record. `UNVERIFIED`: whether Lotus's and Latte's sub-3:1 planes carry glyphs in practice — the census is grep-derived (two renderers), never an app run.
- **Alucard Classic — the spec's official Dracula light variant (`#FFFBEB`) — is deferred, not rejected.** It is exactly the case the two-axis design was bought for, and the registry now makes it cheap: add a light reading to Dracula's row, and `modes: ["dark"]` becomes `["light", "dark"]` with no change to the mode logic or the `system` resolution. It also means "Dracula" currently labels a *variant* of a *family*; if Alucard ever ships, the picker names the variant.

# Dracula

The record below predates the other six and is kept as written: Dracula is the scheme the ladder and the contrast floors were originally designed against, and its numbers are the ones several ADRs quote.

The persisted `palette: "dracula"` reading is a PARTIAL diff over the shared `.dark` tokens: **120 declarations (89 structural + 25 file-type descriptors + 6 ramp), inheriting 54** of `.theme-default-dark`'s 168. Both figures are what `paletteCompleteness.test.ts` asserts, not recalled — an earlier version of this doc said 115 / 84 / 59, and the live gate contradicted all three. That is the lesson ADR 0027 records as **"count it, do not recall it"**, after retracting three separate self-reported facts of its own; every number in this doc is a re-measurement, and the gates that produce them are named beside each one.

Syntax highlighting for this Palette is the registry's `dracula` entry, and because Dracula pins the mode it resolves to that theme in every mode — `paletteModeFor` answers `dark` before `shiki.light` is ever consulted, which is why its `shiki.light` is `undefined` rather than a guess.

## The token map

`src/index.css` is the authority; `src/lib/paletteCompleteness.test.ts` is the gate (it rejects any hex in the block that <https://draculatheme.com/spec> does not publish). Surfaces walk the spec's elevation ladder:

- `#21222c` — inputs, popover header (recessed within a panel; `#191a21`, the bottom rung, is `--color-terminal-bg` and paints nothing — see below).
- `#282a36` — the page, AND the sidebar: `--color-sidebar` is an alias of `--color-background`, because the chrome bar is `bg-background` (`App.tsx`, `data-testid="chrome-bar"`) so sidebar and menubar are one plane. `--color-tab-active` sits here too.
- `#343746` — header, panel, tabs, menus, popovers, toasts, tooltips (the floating step; header and panel are one band and so share a rung, as in default dark), plus `--color-context-track`.
- `#424450` — cards, menu hover, `bg-secondary`, the inline-code chip (`tag` / `tooltip-tag`). NOTHING rests above it: `secondary`/`tag` used to be `#44475a`, which is brighter than `card`, an elevation inversion default dark does not have.
- `#44475a` is spec **Selection** — reserved for selection and pressed states, and appearing nowhere as a border or a resting surface. `--color-border` is instead Current Line `#6272a4`, the spec's literal "subtle borders" instruction, reaching card/tab/input/popover borders through aliases.
- Four deliberate departures from the spec, all stated in the block's own doc-comment: (1) status **text** keeps the bright syntax hues while the **Functional** palette drives fills, borders and focus (`#815cd6` brand = the spec focus ring via `--color-input-border-focused`; `#0081d6` interactive borders) — and where even a syntax hue fails on a real background the spec's ANSI *bright* variant is used rather than a new hue, which is why `destructive` and `diff-removed` are `#ff6e6e`; (2) `--color-foreground-subtle`/`-subtlest` are Foreground at 70% / 55%, not a hue, so they stay on-palette at every elevation; (3) Selection is never a border; (4) the 25 `--color-file-*` **Identity color** hues are off-spec on purpose — 11 hues cannot name 25 file types, and the hue IS the signal. The gate allow-lists 24 of them by name; `file-css` needs no exemption (`#bd93f9`, already on-spec — the Default palette's `#7e57c2` is 2.73 on Dracula's **slab** `#282a36`, under the 3:1 glyph floor; it clears the page `#21222c` at 3.03, so the slab is the surface that decides. This sentence used to quote 2.73 against "the page", which was true before ADR 0027's one-step-down amendment moved the page off `#282a36` — see Open follow-ups).

## Contrast ceilings (constraints on any future palette, not defects to fix)

Re-measured against the composited surfaces the tokens actually render on. These are walls, not unfinished work.

- **No spec-published red clears 4.5:1 on the elevated surfaces.** `#ff6e6e` is the brightest red the spec publishes: 5.23 on the page, **4.33 on `#343746`**, 3.54 on `#424450`, 3.36 on Selection — and lower still on tinted diff rows (4.47 on a page-tinted row, 4.02 on the transcript column's, 3.72 inside `ToolCallCard`, where a tool diff actually renders). The only spec-published value near enough to red to clear 4.5 on the floating step is AnsiBrightMagenta `#ff92df` (5.86 there) — Pink, the hue this palette gives string literals: trading a 0.17 shortfall for a real ambiguity. The gate pins 4.3 / 3.3 there and *fails if either ever clears 4.5*, so the exemption cannot outlive its reason.
- **`--color-border` is 2.51 on panel and 2.05 on card — by spec instruction.** `#6272a4` clears the 3:1 UI floor on the page (3.03) and the input well (3.36) and nowhere else; borders inside floats are structurally told apart by the container's own edge, not by the rule's contrast.
- **The Functional colours fail as text though they are correct as fills**: on the page, Functional Green 3.43, Red 3.74, Orange 4.66 (4.5 is the spec's own floor, and the spec does not scope it to body text — treating the syntax hues as exempt is our reading, not its words). The ratio that decides the split is consumption: 31 `text-destructive` against 12 `bg-destructive` in `src/components/` + `App.tsx`, tests excluded.
- **A palette that omits an Identity color does not fail — it silently resolves through `.dark` to `@theme`'s light-safe reading**, and 5 of the 25 descriptors fall under 3:1 on `#282a36` that way (`file-ts`/`file-py` 2.97, `file-sass`/`file-graphql` 2.88, `file-css` 2.73). That is why the palette test is a completeness test, not a spot check.

## Tokens that paint nothing (say so plainly before someone "fixes" them)

- **22 `--color-terminal-*` tokens, 21 of which are inert**: there is no terminal surface — no terminal component, no `xterm`/`node-pty`/`portable-pty`/`alacritty`/`vt100` dependency, and zero `(bg|text|border)-terminal-*` consumers. The palette owns them anyway because the spec publishes the 16-colour ANSI table (copying beats inventing) and a half-owned palette is the failure mode the completeness test exists to prevent. **One is live, by alias rather than by class:** `@theme` defines `--color-icon-blue: var(--color-terminal-bright-blue)`, so markdown links (`MessageBubble.tsx`) and diff `@@` hunks (`DiffBlock.tsx`) take AnsiBrightBlue `#d6acff` — 7.60 on the page, 6.29 on the panel, 5.15 on a card. That alias is the ONLY consumer of any terminal token outside `index.css`.
- **`--color-background-win-alt` has zero JSX consumers** and paints no titlebar (ADR 0027 retracts the comment that called it one); the chrome bar is `bg-background`. It survives because `--color-background-alt` derives from it, and that DOES paint the content column (`ChatStream`, `SidePane`) — `#343746` at 60% over the page = `#2f3240`. `--color-card-selected` (`#44475a`) is in the same class of forward declaration: no JSX reads `bg-card-selected`; the sidebar rows paint `bg-selected`.
