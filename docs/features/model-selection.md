# Model + thinking-level selection

The desktop lets the user select a session's model and thinking level — live OR stored (#154) — over the `configOptions` mechanism — the options are SYNTHESIZED in-process by the desktop's native harness (ADR 0011 / 0022: the desktop IS the harness — there is no external agent to advertise them). The controls themselves live in the **Side pane** (the **session config block**), not in the transcript header.

## How it works

- **Harness (in-process, `src-tauri/src/agent/session/mod.rs`)** is the source of truth: `synthesize_catalog_config_options` builds the `config_options` from the `ModelCatalog` (the EFFECTIVE catalog — the base models + the user's Settings providers, ADR 0014 — so a user-provider model can be switched TO mid-session, not just the base ones):
  - a **model** selector (`id: "model"`, `name: "Model"`, `category: "model"`, `type: "select"`) — options are the catalog's `selectable()` models: `value` the composed `"<provider>/<id>"` key, `name` the bare model id; `currentValue` the session's current model key;
  - a **thinking-level** selector (`id: "thought_level"`, `name: "Thinking"`, `category: "thought_level"`, `type: "select"`) — options are the CURRENT model's advertised `thinking_levels` (display name the capitalized level, `"medium"` → `"Medium"`); `currentValue` the session's current level (empty when none is set); the selector is ABSENT when the model advertises no levels.
  - It runs at session start AND resume (the `SessionInfo.config_options` — a resume re-synthesizes fresh state from the stored `capabilities.model` + the catalog, with the stored `thinkingLevel`), and after every `set_config_option`.
- **Rust (Client, `src-tauri/src/commands/sessions.rs`)**: the `set_session_config_option` command → `SessionManager::set_config_option`: validates the value (a model: the composed key must resolve in the effective catalog; a level: non-empty), then ONE liveness probe — `WorkerManager::handle_for(session_id).is_some()` — decides the transport. **A live session** gets the change over IPC: `SessionManager::send_config_to` → `WorkerHandle::send_config`, the `Config` frame on the Worker's stdio JSONL, which the Worker's `AgentLoop` applies when idle (its `set_model` / `set_thinking_level`; a model switch also applies the ADR 0015 minimal-surprise thinking-level reset: the level is KEPT when valid for the new model, replaced — the new model's remembered level, or `None` — only when the new model doesn't support it). **A session with no live Worker** sends no frame at all: the session's own `capabilities_json` row is what carries the change (#154, see **Persistence**). Either way it then mirrors the change on the per-session config state (the re-synthesizer's source), RE-SYNTHESIZES the options from the catalog, and emits the `config_option_update` frame (the loop does NOT emit one itself — the client owns the frame). That mirror + re-synthesize + emit now runs on BOTH arms — the emit is no longer gated on a send having happened, only on the command having got this far. The mirror-on-success rule survives only where a frame was actually attempted: `send_config_to`'s error propagates, so a Worker that died mid-call fails the command instead of reporting a success the loop never applied (and within the model arm's reset sub-path, a failed `send_config_clearing_to` simply leaves that one mirror untouched). The old reason for gating the emit — a full / closed control queue meaning the loop never applies the change — was the in-process `ControlCmd` channel, which is crate internals reached only through the frame; it is not a desktop-side condition, and it is no longer what the desktop branches on.
- **Persistence**: while the Client does not persist `config_options` directly (a stored session's `SessionInfo.config_options` is SYNTHESIZED ON READ by `list_sessions` from the row's stored `capabilities.model` / `thinkingLevel` through the effective catalog — a stale / unknown model key falls back to the resolution chain, never a hard error), a mid-session model switch DOES persist the new model key and re-synthesised capabilities (`thinkingLevel`) to the session's database row (`SessionManager::set_config_option` (in `src-tauri/src/agent/session/mod.rs`) via `Db::update_session_capabilities` (`src-tauri/src/storage/db.rs`)), ensuring the switch survives app restarts. Stored-session selectors are POPULATED and **ENABLED** (#154): `set_session_config_option` persists the change and returns the re-synthesised `SessionConfigOption[]` even when no Worker runs, and the frontend applies that response through `applyConfigOptions`, so the trigger moves to the new value without a resume. The harness is the source of truth. One honest limit on that persistence, accepted with #154 rather than designed away: ADR 0015's resume chain is **remembered > stored > settings default**, so the row's `thinkingLevel` is BEATEN by the `settings.json` remembered level on resume — which is why the `thought_level` arm writes BOTH rungs (the remembered map for the session's model, then the row) and the user's choice therefore survives. It survives only for as long as the remembered rung still carries it: that map is keyed by MODEL, not by session, so a later level change made in any other session on the same model overwrites the entry, and a remembered entry the model no longer advertises is ignored outright — in both cases the next resume boots whatever the stored rung says, not what this session was last set to. Fixing that properly would mean re-ordering ADR 0015's chain, which is deliberately NOT proposed here; the cheap correct statement is the limitation.
- **The context bar's window is DERIVED on the same read** (ADR 0076): `list_sessions` resolves the row's `capabilities.model` against the effective catalog and takes `context_usage.window` from THAT model, replaying only `used` from `sessions.context_usage_json` — `used` is a measurement of the session, `window` is a property of the model, and the persisted snapshot froze both. It resolves `capabilities.model` a SECOND time rather than reusing the value `config_options` resolved, because that one falls back to the resolution chain for its own display purpose and would pair `used` with an unrelated model's window; an unresolvable key therefore keeps its stored snapshot. A **Provider** refresh in Settings re-reads the row (`listSessions(true)` + `mergeRefreshedSessionRows`) so a CLOSED session's bar shows the corrected window without a restart, and merges ONLY the per-id maps — `setHistorySessions` re-splits the lists and is forbidden mid-run — while skipping ids that are LIVE, whose in-memory snapshot is newer than any row on disk.
- **Frontend** keeps per-session `configOptions` in the sessions store — seeded on start/resume (the `SessionInfo.configOptions`), replaced wholesale by `config_option_update` notifications (the `set_session_config_option` command's response is applied through `applyConfigOptions` — the same wholesale replace), cleared on close — and renders the two controls as **Side pane** config LINES (`SessionConfigBlock.tsx`, pinned below the pane's scroll area; they left the composer's bottom row, so the composer carries neither). Looked up through the shared derivations in `src/lib/sessionConfig.ts` (`category` match with `id` fallback, `type === "select"` + non-empty `options`) so each control subscribes to its derived value and re-renders only when that changes; the controls are ENABLED for a stored session (the backend persists the change without a Worker, #154) and disabled while a set request is in flight — plus, for the **Model** picker only, PER ROW: a catalog model the engine cannot speak renders as a disabled row that says why (issue #9; see **Per-row disabled rows** below); the Model picker's option list comes from the LIVE model catalog store (`useModelCatalog`, filtered to the configured providers) rather than from the session's snapshotted option list, so adding or refreshing a provider in Settings reaches an ALREADY-OPEN session's picker; a transient inline error on failure auto-clears after 5 s. See **Selector visibility** below for when the thinking line renders at all.

## Selector visibility (the Client renders ONLY what the harness emits — PR #56)

The harness is the single source of truth for whether a thinking-level selector EXISTS: `synthesize_catalog_config_options` pushes the `thought_level` option ONLY when the current model's `thinking_levels` is non-empty, and the Client honours that instead of manufacturing a control. `SessionConfigBlock` renders the Side pane's Reasoning line if and only if `findConfigOption(configOptions, "thought_level", "thought_level")` returns an option — which it does not for a model advertising no levels, for a `select` with empty `options`, for a session whose config options are absent, or with no active session. One rule, no disabled stub: a dropdown that can never open is a lie about the model. **That rule holds for the THINKING line exactly as written** — the line appears or it does not, and no row of it is ever greyed out. The Model picker is the one place with a per-row disabled state, and it is a different kind of thing: the line always exists and always opens, and only individual ROWS inside it are inert (see **Per-row disabled rows in the Model picker** below).

The Model line is deliberately NOT gated this way, and the asymmetry is load-bearing: a model selector is meaningful for ANY session (the user can always switch to a model that has levels, and `ModelPicker`'s catalog comes from Settings rather than from the session's option list), whereas a thinking selector is not. So a session with no levels shows two lines (Model, then Context) and a pane with no session shows the Model stub and an empty 0% track. `CONTEXT.md`'s **Session config block** entry carries the same rule.

### Per-row disabled rows in the Model picker (issue #9)

The one exception to "no disabled stub", and it is NOT a line-level exception: the Model line always exists and always opens. Inside the picker, an individual catalog row can be **disabled with a reason**.

**Where it comes from.** `Model::is_selectable()` (fulcrum `catalog.rs`) is the ONE selectability predicate: `supports_tools` AND the model's `api` parses to a supported `WireApi`. `ModelDto` projects it as `selectable` alongside `supportsTools` (`src-tauri/src/commands/settings.rs`, `From<&Model> for ModelDto`) — projected, never recomputed, because a second copy of the predicate is how a picker starts offering a model the catalog refuses. `list_models` is UNFILTERED (since #154 the picker's rows come from the live catalog store, which is what makes a Settings change reach an open session), so an unselectable model reaches the picker anyway and the row is the only place the user learns it exists but cannot be used.

**What the row says.** Both surfaces that pick a model the harness will RUN derive `disabled` + `note` from the same function — `modelSelectabilityNotice` (`src/components/ModelPickerDialog.tsx`) — so they cannot disagree about a row: the session's Model line (`SessionConfigBlock`) and the **subagent** per-agent Model row (the Agents modal, via `modelItemsFromModelDtos`). `disabled: m.selectable === false`, NEVER `!m.selectable` — an ABSENT field must not disable, or one missing field on the wire greys out the entire picker. The note names which half failed, because the two halves have two different fixes: `supportsTools === false` → `no tool support advertised` (the provider's metadata), anything else → `unsupported wire` (its API mode).

**The four-value wire vocabulary.** `WireApi` has FOUR values — `openai-completions`, `anthropic-messages`, `openai-responses`, and `litellm` — and `WireApi::is_supported` accepts all four, so all four are selectable on the wire half. `litellm` is a DISCOVERY MODE, not a fourth wire (its wire is `openai-completions`; ADR 0026), which is why the older wording elsewhere says three. **ADR 0024's "the three supported wires" (`docs/decisions/0024-multi-wire-providers.md`) predates the `litellm` discovery mode and was deliberately NOT back-edited** — the value that would correct it arrived with ADR 0026, and a reader arriving from this change is pointed at ADR 0026, not at 0024. This file is the live doc for selection, so the four-value vocabulary is recorded HERE.

**What is deliberately NOT covered.** The Settings model lists (`settings/GeneralSection.tsx`'s Default-model and session-naming pickers) still render an unselectable model as usable, on purpose: configuring a DEFAULT model is a flow where the user may be about to fix the provider's wire in Settings itself, and greying the row out there hides the thing they are in the middle of repairing. ADR 0026's 2026-11-08 amendment carries the same residual.

### Known accepted consequences (pre-existing, knowingly NOT fixed)

Recorded boundaries and accepted limits:

1. **A hidden level can still be live.** `Model::supports_thinking_level` (`src-tauri/src/agent/harness/catalog.rs`) soft-passes when `thinking_levels` is EMPTY, so the `"model"` arm of `set_config_option` treats the current level as valid for a level-less model and SKIPS the ADR 0015 reset. `config_state.thinking_level` therefore stays `Some("high")` while the synthesizer omits the selector — a session can run a non-default level with no visible Reasoning control, and the level reappears in the line if the user switches back to a level-capable model. Before PR #56 the stub painted this state as `○` ("off"), which was already wrong; an absent line is not worse. Do not read the missing line as proof the level is unset.
2. **A stored session's line can describe a different model.** `list_sessions` resolves a stored row's `capabilities.model` through the effective catalog and falls back to `resolve_native_model` (the resolution chain) when the key no longer resolves, then synthesizes the options for THAT model — so a stored session's Reasoning line can be gated by a model it never ran. The Client faithfully renders the list it is handed; the line is not a record of the session's own capability.
3. **Provider-ambiguous bare-id lookup.** `ModelCatalog::get` (`src-tauri/src/agent/harness/catalog.rs`) matches bare `m.id == id`, so two providers exposing the same model id resolve to whichever entry is first in the catalog vec. Status: accepted/open, with the mitigating fact that no request-path caller exists — its only call sites are its own tests (`src-tauri/src/agent/harness/catalog.rs`). Live request paths use the composed-key discipline (`m.provider == key.provider && m.id == key.id`, `SessionManager::set_config_option` and `resolve_composed_model` in `src-tauri/src/agent/session/mod.rs`).
4. **A same-key baseUrl edit does not re-point a live session (2026-10-29, #120).** Saving Settings only writes the file (`save_settings` in `src-tauri/src/commands/settings.rs`, reached from `SettingsPage.tsx` `commitProviderField` -> `src/lib/tauri/commands/settings.ts` `saveSettings`); nothing pushes to live sessions. The Settings page's Refresh affordance (`SettingsPage.tsx` `refreshProvider`) does reach live sessions via `list_models`' `force_refresh` arm (`src-tauri/src/commands/settings.rs`) -> `SessionManager::refresh_live_models`, but that push preserves the session's own `base_url`/`api_key` (`SessionManager::refresh_live_models` in `src-tauri/src/agent/session/mod.rs`), and the composed model key is unchanged, so the provider instance is not rebuilt. Net: to move a live session to a new URL, the user must switch models (or restart the session).

### #154 residuals (added 2026-11-06 — the live-catalog picker and selectors-enabled-when-stopped)

These three are the known limits left standing by #154. The first is **open work**; the other two are decisions, recorded so nobody "fixes" them back.

5. **`open work` — adding a provider still races the settings write.** `SettingsPage.tsx` `addProvider` captures the new id and fires `useModelCatalog.getState().loadModels(addedId)` — which MUST be forced, because a plain `loadModels()` early-returns once `loadedOk` is set by the boot read in `App.tsx`, and that no-op was the actual reported bug. But the preceding `update(...)` reaches `useSettingsDocument`'s `patch`, which ends in **`void saveSettings(next)`** — fire-and-forget, never awaited — while `list_models`' forced arm re-reads `settings.json` from disk (`load_settings` in `src-tauri/src/commands/settings.rs`). So the forced read can resolve against the PRE-add file, and the new provider's rows arrive on the next plain read or Refresh instead of immediately. **No frontend test can see this** — the IPC wrapper is mocked, so the assertion checks that the store got populated, not the ordering. Closing it properly means either awaiting the save or refreshing the catalog from the Rust write that lands the file; that is backend work, deliberately not attempted here. `removeProvider` is unaffected by the race and deliberately does NOT refresh: the picker filters the store's `models` against the CONFIGURED providers, and `patch` publishes the new provider list synchronously, so a removed provider's rows vanish on the next render with no network call — a re-fetch could only return them again. That non-refresh is pinned by a guard-rail test.

6. **`accepted` — renaming a provider does not refresh the catalog at all.** Same race as 5, but unawaitable in a way that makes it unclosable from the frontend: after a rename the new id's catalog rows wait for the next plain read. The provider NAME cue in the picker updates reactively (it comes from `useSettings`), so what is delayed is the row list, not the label. The alternative — firing a refresh whose ordering is unspecified — was rejected: it would pass every test while sometimes resolving the old provider list, which is worse than an honestly-documented lag. The rationale sits as a comment at the `commitProviderField` call site.

7. **`recorded, not open work` — `set_config_option` gained a new error arm.** With #154 the command now hard-errors when no `Db` is attached (message naming the missing `WorkerManager` attachment) where it previously returned `UnknownSession` from the old pre-check, and where the transport siblings (`send_prompt` and friends) still use a soft `if let Some(db)`. The asymmetry is intentional and converges with the other DB-backed commands (`resume_native_session`, `establish_worker_session`, `list_sessions`), on the reasoning that a session cannot exist without an attached database — `setup` always attaches one and every test builder attaches one, so nothing observable changed in production. It is recorded because it is a new failure mode on a command the frontend calls, and because a reader comparing it to `send_prompt`'s `if let Some(db)` should not "harmonise" them. A companion accepted behaviour: a no-live `model` switch drops a stored thinking level the new model does not advertise — that is the existing ADR 0015 minimal-surprise reset, now applied to the row-backed level read, and it is pinned by a test rather than incidental.

## Wire shape facts (the synthesized JSON — do not re-research)

`synthesize_catalog_config_options` emits plain JSON (no crate types — the `agent-client-protocol` crate is gone, ADR 0022):

- Each option: `{ id, name, category, type: "select", currentValue, options }` (camelCase `currentValue`; `category` snake_case — `"model"` / `"thought_level"`). The frontend's `SessionConfigOption` (`src/lib/tauri.ts`) models `type: "select" | "boolean"` and `options` as a flat `(SessionConfigSelectOption | SessionConfigSelectGroup)[]` — the synthesizer emits FLAT `{ value, name }` entries (no groups, no `description`).
- The `set_session_config_option` command returns the re-synthesized `config_options` array (the frontend applies it through `applyConfigOptions`); the emitted `config_option_update` frame carries the same array — the store replaces wholesale, so the order of the two paths is irrelevant.
